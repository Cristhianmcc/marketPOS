## Hallazgos prioritarios

### H01 — Crítico: cambio de tienda permite suplantar al propietario

**Ubicación:** `src/app/api/setup/switch-store/route.ts:10-62`.

Solo se exige estar autenticado. El `storeId` recibido selecciona una tienda y
su primer OWNER; `setSession` adopta su identidad y rol. No se exige ser
superadmin, pertenecer a la tienda ni conocer la contraseña. Si se suministra
`userId`, tampoco se comprueba que pertenezca a esa tienda o esté activo.

**Confirmación aislada:** una sesión CASHIER de tienda A solicita tienda B;
respuesta 200 y nueva sesión OWNER de B. Este problema existe incluso para
elevar el cajero al propietario de su propia tienda.

**Corrección:** política explícita de cambio de tienda, identidad estable,
autorización de pertenencia/rol y validación de usuario activo. Probar cajero,
owner, superadmin, usuario de otra tienda y usuario inactivo.

**Estado en `feature/sunat-beta` (18/10/2026): corregido y verificado.** La ruta
exige SUPERADMIN, rechaza tiendas archivadas y solo adopta un OWNER activo de la
tienda indicada. `scripts/audit-pos-isolated.cjs` comprueba rechazo de CASHIER,
OWNER, usuario cruzado, usuario inactivo y tienda archivada, además del caso
permitido para SUPERADMIN.

### H02 — Crítico: secretos de configuración incluidos en la distribución

**Ubicación:** `desktop/scripts/prepare-build.js:43-54` y `desktop/package.json`
(`extraResources`).

La preparación copia el `.env` raíz a recursos y al servidor. Se confirmó que
ambas copias existen en `dist-electron-20260401-193140/win-unpacked/resources` y
contienen las claves de BD local/cloud, SESSION_SECRET, Cloudinary,
LICENSE_API_KEY y SUPERADMIN_PASSWORD_HASH. No se muestran sus valores ni se
comprobó si las credenciales siguen vigentes.

**Impacto:** quienes reciben el paquete pueden leer su configuración; un
secreto de sesión compartido o credenciales cloud no deben distribuirse como
recursos de un cliente. No se afirma que haya habido acceso indebido.

**Corrección:** generar configuración mediante lista permitida de valores no
secretos; credenciales locales por instalación; operaciones cloud mediante API
autenticada con alcance limitado. Si estos valores se distribuyeron y siguen
vigentes, rotarlos de forma coordinada y revisar los paquetes publicados.

### H03 — Medio: el respaldo automático programado no se ejecuta

**Estado:** corregido y verificado el 20/10/2026 en `feature/sunat-beta`.

**Ubicación:** `desktop/src/backupScheduler.ts`,
`src/app/api/desktop/backup-context/route.ts`,
`src/app/api/backups/export/route.ts` y `src/app/settings/backups/page.tsx`.

El programador anterior consultaba una ruta inexistente y omitía el respaldo
sin registrar el error. Electron ahora consulta una ruta interna autenticada
que enumera todas las tiendas activas y exporta cada una usando el token efímero
del servidor local. El flujo web de exportación conserva sus controles de
sesión, rol y límite de solicitudes.

El estado se guarda en `backup-status.json` dentro de `userData`: último intento,
último éxito, próxima ejecución, archivos creados y error. La pantalla de
respaldos muestra esa información, permite ejecutar el ciclo en el momento y
abrir la carpeta. Un fallo programa un reintento posterior y queda visible; una
ejecución en curso no puede iniciarse nuevamente por el mismo programador.

`npm run test:backups:isolated` verificó dos tiendas activas, autenticación
interna, checksum del ZIP, inclusión del archivo fiscal, persistencia después de
reiniciar y exposición del fallo de API. El restaurador existente también se
ejecutó en sus transportes ZIP directo y multipart con un respaldo
representativo, Prisma simulado y transacción completa; no se escribió ninguna
base real. La auditoría aislada, TypeScript de Electron, `git diff --check` y
`npm run build:only` pasaron. Falta como aceptación operativa observar la tarea
por intervalo en un paquete instalado y restaurar una copia en una instalación
desechable antes de una entrega a clientes.

### H04 — Alto: actualización del esquema acepta pérdida de datos

**Estado:** corregido y verificado el 20/10/2026 en `feature/sunat-beta`.

**Ubicación:** `desktop/src/updater/runMigrations.ts`;
`prisma/migrations/20261020000000_baseline/migration.sql`; `package.json`;
`scripts/test-migrations-isolated.cjs`.

La migración base contiene el esquema PostgreSQL completo. El runner usa
`prisma migrate deploy`, rechaza la ausencia de migraciones y eliminó todas las
caídas a `db push --accept-data-loss`. Tampoco ejecuta el antiguo bloque de
parches SQL antes de migrar. `npm run build` delega a `build:only`, por lo que
compilar no modifica la base configurada.

Para adoptar una base creada por versiones antiguas, primero ejecuta un diff de
solo lectura entre la base y el datamodel. Solo si el resultado es idéntico marca
la migración base como aplicada; una diferencia detiene el inicio sin marcar
migraciones ni cambiar datos.

**Evidencia:** `npm run test:migrations:isolated` levantó PostgreSQL 15.4 incluido
en una carpeta temporal y pasó instalación limpia (45 tablas y un registro de
migración), adopción de una base legada idéntica y rechazo de una base con una
tabla ajena. No se conectó a Supabase ni a una base real. La suite aislada añade
un control estático para evitar que reaparezcan las rutas destructivas.

### H06 — Alto: anular una venta no repone los lotes consumidos

**Ubicación:** `src/app/api/sales/[id]/cancel/route.ts:111-175`;
checkout `:1113-1175`.

Checkout descuenta `ProductBatch.quantityAvailable` y crea movimientos con
`batchId`; cancelar solo incrementa `StoreProduct.stock` y crea movimiento sin
lote. Tras vender y anular un producto FEFO queda stock general recuperado pero
disponibilidad por lote inferior. El siguiente checkout puede rechazar stock.

**Corrección:** invertir exactamente los movimientos/lotes de la venta en una
única transacción, conservando trazabilidad y definiendo qué ocurre con un lote
ya vencido/inactivo. Probar venta que consume varios lotes y su anulación.

**Estado en `feature/sunat-beta` (18/10/2026): corregido y verificado.**
`cancelSaleLocally` repone el stock general y cada lote del snapshot FEFO dentro
de la misma transacción. La prueba aislada restaura una venta distribuida entre
dos lotes y confirma las cantidades y los dos movimientos de ajuste.

### H07 — Alto: doble anulación puede duplicar la devolución de stock

**Ubicación:** misma ruta de anulación, comprobación previa `:56` y transacción
`:111`.

El estado se lee antes de entrar a la transacción. Dos solicitudes pueden ver
la venta vigente y ambas poner total cero e incrementar stock. No hay transición
condicional o lock de la venta que haga que solo una anulación tenga efecto.

**Corrección:** estado de anulación explícito/transición atómica, idempotencia
persistente y devolución una sola vez. Reproducir con dos solicitudes concurrentes
contra una base descartable. Evidencia de código; no se forzó en la BD real.

**Estado en `feature/sunat-beta` (18/10/2026): corregido y verificado en prueba
aislada.** La anulación reclama la venta mediante `updateMany` condicionado a
total distinto de cero dentro de la transacción. Dos solicitudes concurrentes
producen un solo ganador y una sola devolución de stock/lotes. Falta mantener
esta propiedad cuando se introduzca un estado explícito de anulación en esquema.

### H08 — Alto: cobros de fiado concurrentes pueden perder actualización del saldo

**Ubicación:** `src/app/api/receivables/[id]/pay/route.ts:98-169`.

El comentario dice «con lock», pero `findFirst` no aplica bloqueo explícito;
se guarda `currentBalance - amount` como valor absoluto. Dos pagos de 30 sobre
saldo 100 pueden crear dos abonos y terminar dejando 70 en vez de 40.
No hay idempotencia del abono ni aislamiento serializable explícito.

**Corrección:** bloquear/actualizar condicionalmente saldo y estado en BD y
persistir clave del pago. Verificar pagos simultáneos, reintento de red, pago
total concurrente y anulación de la venta mientras se cobra.

**Estado en `feature/sunat-beta` (18/10/2026): corregido y verificado en prueba
aislada.** El endpoint decrementa el saldo con `updateMany` condicionado por
tienda, estado abierto y saldo suficiente. Cada intento usa una clave de
idempotencia persistida como identificador determinista del abono, por lo que
un reintento devuelve el pago existente y una carrera por la misma clave se
revierte por completo. La interfaz conserva la clave mientras el modal está
abierto. La prueba concurrente registra dos abonos de 30 sobre saldo 100, deja
saldo 40 y confirma que repetir uno de ellos no crea un tercer pago.

### H09 — Alto: órdenes de compra permiten productos de otra tienda

**Ubicación:** `src/app/api/purchase-orders/route.ts:69-106`;
`src/app/api/purchase-orders/[id]/route.ts:85-107`.

Se valida pertenencia del proveedor, pero los `storeProductId` de items se crean
directamente. Al recepcionar, el producto se actualiza solo por ID. El esquema
tiene FK al producto, sin una relación compuesta que obligue a la misma tienda.

**Confirmación aislada:** producto identificado como ajeno es aceptado con 201,
sin ninguna consulta de pertenencia. La prueba no modifica stock real.

**Corrección:** validar todos los productos activos y su tienda antes de crear
la orden y nuevamente al recepcionar; cantidades/costos finitos y positivos,
política de roles y pruebas entre tiendas.

**Estado en `feature/sunat-beta` (18/10/2026): corregido al crear la orden.** El
handler valida identificadores, cantidades y costos, consulta todos los
productos por `storeId` y rechaza cualquier producto ausente o ajeno antes de
abrir la transacción. La prueba aislada H09 confirma el rechazo con estado 400.
La validación redundante durante la recepción permanece cubierta por el filtro
de tienda existente y debe conservarse al corregir H10.

### H10 — Alto: recepción puede vincular un movimiento al lote de otro item

**Ubicación:** `src/app/api/purchase-orders/[id]/route.ts:48-99`.

`batchesCreated` acumula lotes de toda la recepción. El movimiento usa el último
lote del arreglo aun cuando el item actual no creó uno. Caso concreto: primer
item con lote/fecha, segundo sin ellos; el segundo recibe `batchId` del primero.

También admite cantidades superiores a lo pendiente y comprueba estado fuera
de la transacción; recepciones simultáneas/repetidas pueden inflar existencias.

**Corrección:** variable de lote por item, validación de pendientes y transición
atómica/idempotente. Si se permite sobre-recepción, definirlo expresamente.

**Estado en `feature/sunat-beta` (19/10/2026): corregido y verificado.** La ruta
valida items, productos activos de la tienda y cantidades pendientes; mantiene
el lote como variable local de cada item. La orden se reclama por su versión
observada dentro de una transacción serializable y los movimientos reciben IDs
deterministas derivados de una clave de idempotencia estable en la interfaz.
Un reintento exacto devuelve la recepción existente. La prueba aislada cubre el
caso lote/sin lote, un reintento sin duplicación, dos recepciones concurrentes
con un solo ganador y una sobre-recepción rechazada sin modificar existencias.

### H11 — Alto: trazabilidad farmacéutica fuera de la transacción y tienda no validada

**Ubicación:** checkout `:1616-1691`, `src/app/pos/page.tsx:1870` y
`src/app/api/patients/medication/route.ts:40-77`.

La tarea de PatientMedication/ControlledBookEntry se lanza sin await tras
confirmar venta; sus fallos solo se registran. La consulta de paciente filtra
tienda, pero aunque devuelva null se continúa usando el patientId original para
crear registros. El handler posterior de medicación sí valida tienda, lo que
no corrige el camino directo del checkout.

El cliente ejecuta además un fallback. Su findFirst previo no es una garantía
contra concurrencia con el insert del servidor. Pueden faltar registros o
duplicarse. El libro se ejecuta solo si hay patientId o número de receta,
aunque otra validación acepta nombre/observación como información de receta.

**Corrección:** paciente válido antes de vender, registro transaccional o outbox
durable e idempotente ligado al item de venta. Revisar regla de negocio del libro
y cancelaciones. No se evaluó cumplimiento médico/legal del módulo.

**Estado en `feature/sunat-beta` (19/10/2026): corregido y verificado.** El
checkout valida paciente, dispensador y receta antes de escribir la trazabilidad,
y crea `PatientMedication` y `ControlledBookEntry` en la misma transacción que la
venta a partir de los `SaleItem` persistidos. Los identificadores deterministas
por item hacen idempotente un reintento exacto. Se eliminó la tarea posterior sin
`await` y el fallback duplicado del cliente; la ruta de compatibilidad deriva los
medicamentos desde la venta persistida y vuelve a comprobar tienda y paciente.
La auditoría aislada cubre paciente ajeno, receta ausente, creación correcta y
repetición sin duplicados. `npm run build:only` también pasó sin ejecutar `db push`.

### H12 — Alto: configuración CORS del servicio de impresión permite cualquier origen

**Ubicación:** `print-service/src/server.ts:593-603,668-683`.

Para un origen no permitido devuelve `Access-Control-Allow-Origin: *`;
no rechaza la solicitud. Configuración e impresión carecen de autenticación,
y PUT acepta valores sin validar tipos. Escucha solo en loopback, pero eso no
equivale a autorización del sitio web que intenta llamarlo. La accesibilidad
desde una web concreta depende también de las restricciones del navegador.

**Corrección:** rechazar orígenes no permitidos, emparejamiento/token local,
validar configuración y evitar interpolar entradas en comandos de shell.
Revisar particularmente el recorrido usbPort -> printUsb -> execSync.
No se ejecutaron payloads de shell ni impresiones para confirmar explotación.

### H13 — Medio: idempotencia débil y sesión incorrectamente comprobada en checkout

**Ubicación:** `src/lib/idempotency.ts`, `checkoutLock.ts`, checkout
`:1218-1286`; `src/app/pos/page.tsx:1651`.

La caché dura 60 segundos en memoria, usa solamente la clave enviada, sin
tienda/usuario/hash de cuerpo. El replay ocurre antes de comprobar usuario y
tienda activos. `getSession` siempre devuelve un objeto y `if (!session)` no
valida que esté autenticado. No implica que cualquier solicitud vacía pueda
crear venta: hay verificaciones posteriores, pero son tardías para el replay.

El cliente genera nueva clave en cada intento; si el servidor confirmó y se
perdió la respuesta, el siguiente intento no recupera la venta ya creada.

**Corrección:** clave persistente por intento de venta, ámbito tenant/usuario,
validación previa de sesión y cuerpo, exclusión atómica en BD. Probar reinicio,
dos procesos y pérdida de respuesta. El lock en memoria no cubre estos casos.

### H14 — Alto: inventario usa lectura y asignación absoluta frente a operaciones concurrentes

**Ubicación:** checkout `:139,1158-1188`; rutas de ajuste y recepción de stock.

Checkout lee stock y después escribe un valor calculado. Una recepción/ajuste
entre esa lectura y la escritura puede perderse. El lock es por cajero y solo
en el proceso. La unicidad/reintento de número de venta mitiga colisiones de
ventas, pero no serializa una recepción o ajuste que no crea número de venta.

**Corrección:** actualización condicional atómica de stock, locks consistentes
en producto/lotes o aislamiento apropiado con reintentos. Verificar mezcla de
venta, recepción, ajuste y anulación concurrentes.

**Estado en `feature/sunat-beta` (19/10/2026): corregido y verificado.** El
checkout consume stock general y lotes FEFO mediante decrementos condicionales
atómicos dentro de su transacción. El ajuste manual aplica su delta y crea el
movimiento en una sola transacción. Los productos sin control de stock conservan
`stock = null`. El helper común rechaza existencias insuficientes o datos que
cambiaron desde la lectura inicial, por lo que la transacción completa se revierte.

`scripts/audit-pos-isolated.cjs` verifica que una recepción concurrente no se
pierda, que dos ventas simultáneas no sobregiren el mismo stock, que un ajuste y
una venta preserven ambos deltas, que una asignación FEFO obsoleta no deje un lote
negativo y que un producto sin control de stock no sea modificado. Todas esas
pruebas pasaron el 19/10/2026.

### H15 — Medio: filtros inconsistentes en resumen de reportes

**Ubicación:** `src/app/api/reports/summary/route.ts:30-160`.

La consulta de ventas excluye total cero y restringe el cajero a sus ventas.
Los agregados de promociones categoría/volumen/n-ésimo usan solo tienda/fecha,
sin esas restricciones. Por tanto pueden incluir descuentos de ventas anuladas
o de otros cajeros dentro de un resumen personal. También cambia lte a lt para
el extremo final. Otros totales globales deben etiquetarse explícitamente.

**Corrección:** reutilizar filtros de la misma población y definir si el reporte
es personal o de tienda. Comparar cabeceras, líneas, descuentos, caja y exportación.

**Estado en `feature/sunat-beta` (19/10/2026): corregido y verificado.** Los
descuentos por promoción general, categoría, volumen y n-ésimo se calculan ahora
sobre los mismos `Sale` ya filtrados. El conjunto exige tienda activa, rango
inclusivo y `total > 0`; además añade `userId` cuando el rol es `CASHIER`. El rol
`OWNER` conserva el alcance de tienda. Una sesión sin `storeId` termina con
`STORE_REQUIRED` antes de consultar datos.

La prueba H15 de `scripts/audit-pos-isolated.cjs` ejecuta la ruta real con Prisma
simulado y comprueba los filtros del cajero, el alcance del owner, los tres
totales especializados y el rechazo de una sesión sin tienda. Pasó junto con las
demás pruebas aisladas el 19/10/2026.

### H16 — Medio: secreto de sesión de reserva público y precedencia inconsistente

**Ubicación:** `src/lib/session.ts:17`, `src/middleware.ts:23`,
`desktop/src/main.ts:1349-1371`, `desktop/src/server.ts:441-450`.

Web y middleware usan una cadena fija si falta SESSION_SECRET. Desktop genera
un secreto por instalación en process.env, pero server.ts expande después
envVars del archivo y solo restaura DATABASE_URL/DIRECT_URL: un SESSION_SECRET
empaquetado prevalece sobre el generado.

**Corrección:** fallar al arrancar sin secreto válido en web; respetar el secreto
individual del desktop y no copiarlo del entorno de desarrollo. Revisar sesiones
vigentes al cambiar secretos.

**Estado en `feature/sunat-beta` (19/10/2026): corregido y verificado.** Web y
middleware comparten `getSessionOptions()` y rechazan un `SESSION_SECRET` ausente
o menor de 32 caracteres; se retiró la cadena pública de reserva. En el desktop
empaquetado, Electron genera y persiste un secreto aleatorio por instalación en
`userData/app-secrets.json`; `server.ts` lo vuelve a imponer después de cargar el
entorno público, por lo que un archivo `.env` no puede sustituirlo. Si el secreto
no puede persistirse, el arranque falla en lugar de crear sesiones que dejarían de
ser válidas en el siguiente reinicio.

Las cinco rutas heredadas de turnos que construían sus propias opciones de
`iron-session` usan ahora la misma configuración y rechazan una sesión sin tienda
antes de consultar el repositorio. La prueba H16 de
`scripts/audit-pos-isolated.cjs` comprueba secreto ausente, corto y válido,
ausencia del fallback, persistencia desktop y precedencia del secreto. Pasaron la
auditoría aislada, TypeScript de Electron y la comprobación TypeScript dirigida de
los archivos afectados el 19/10/2026. Rotar el secreto invalida las cookies de
sesión existentes y requiere volver a iniciar sesión.

### H17 — Medio: exposición de diagnóstico y confianza en header falsificable

**Ubicación:** `src/app/api/debug/catalog/route.ts`,
`src/app/api/desktop/license/route.ts`, `src/app/api/sync/push/route.ts`.

Debug catálogo no exige sesión y puede devolver ajustes de todas las tiendas o
stack de errores. Desktop license/sync usan `x-desktop-app: true` como único
control inicial, que cualquier cliente HTTP puede enviar. Middleware excluye API.

**Corrección:** cerrar debug en producción y autenticar comunicaciones internas
con un secreto por instalación y límites de despliegue. Un header booleano no
prueba procedencia. Valorar exposición real según servidor local/web.

**Estado en `feature/sunat-beta` (20/10/2026): corregido y verificado.**
`src/lib/desktopInternalAuth.ts` valida en tiempo constante un token interno de
al menos 32 caracteres. Electron genera el token al iniciar el servidor local y
lo transmite sin exponerlo al renderer en los flujos normal, rápido, de
rearranque, licencia, sincronización cloud y cola de tareas. Las rutas
`/api/desktop/license`, `/api/sync/push` y el procesador SUNAT interno rechazan el
header booleano anterior y exigen el token. `/api/debug/catalog` responde 404 en
